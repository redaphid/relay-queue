## Findings worth keeping

**The coordinator guard is not the main friction.** Its escape hatch is
delegation, and it works. The thing with no escape hatch is the Claude Code
**auto-mode classifier** above it, which refuses any mutating brief from an
auto-seated coordinator. Evidence in the New metamcp tab: "I attempted the
dispatch - the auto-mode classifier refused it ... That needs your shell or an
interactive session." The same classifier blocked this session twice tonight
from launching a subagent, until the owner switched to manual permissions.

**A session rooted above the repo gets no guard at all.** There is no
`~/Projects/.claude/settings.json`, so a session rooted at `~/Projects` runs
unguarded against this repo - `git commit`, `kill`, `docker`, `node` all
succeed. This is the exact hazard `SKILL.md` documents for the spawn cwd:
"default-deny becomes default-allow" with no error and no log line. **The new
worktree fence inherits this** - it binds sessions rooted in relay-queue, not
sessions rooted above it.

**A proposal that was flagged and deliberately NOT acted on:** adding
`--permission-mode bypassPermissions` at `autoseat.js:499` to unblock
coordinators. That disables permission checks for every auto-seated agent. It
contradicts the "never weaken a security control" rule now in the global
CLAUDE.md. Recorded as a finding, not a recommendation.

## Known gaps in the new guard rule

1. **Write/Edit only.** `sed -i`, `cat >`, `tee`, `>>` still write the live
   checkout freely from a subagent. So do `git checkout`, `git merge` and
   `git stash`, which are deploys with no Write-tool equivalent.
2. **The fence teaches the workaround.** A blocked `Edit` followed by a
   successful `sed -i` converts a visible failure into a silent one: the audit
   log records the denial, not the write that followed.
3. **`.claude/` is exempt**, so any subagent can edit the guard to delete the
   rule in one allowed call. The exemption must exist or the guard becomes
   unfixable from inside a session, but it means this fences mistakes, not
   determination.
4. **`ROOT` is hardcoded**, deliberately - deriving it from `__dirname` would
   make every worktree fence itself. But the file is now machine-specific and
   on a collision course with the open `wsl-guard-paths` worktree. A merge
   conflict there would be lucky; silent semantic divergence would not.
5. The deny message reuses `deny()` boilerplate whose step 1 is "DELEGATE IT.
   Spawn a subagent... Subagents are exempt from this guard" - now false for
   this rule. A `denyAgent()` variant with its own advice block is the clean fix.
